# Исправления спецификации и дефекты, найденные при реализации

WORLD-0.4 сохранена как исходный документ. Нормативной для кода является WORLD-0.5.0. Здесь отдельно перечислены изменения проектных решений и ошибки, действительно выявленные тестами/прогонами; это не список выдуманных «потенциальных багов».

## Уточнения, которые не следует считать уже выполненной игровой моделью

- Attraction и некоторые параметры романтики сохранены как расширяемые данные, но автоматического развития романтического статуса нет.
- Наблюдение текущего неудовлетворительного результата после срока не всегда доказывает, что обещание было нарушено: предмет мог измениться позже. Общий вывод требует правил над временными свидетельствами.
- Для отказа используются нейтральные отношения; не всякий отказ — конфликт.
- Цена сознательной лжи и гипотеза о злонамеренности — не одно число. Серверный audit-label не является доказательством для игрока.
- Время занятости представлено интервалами/резервами. Публикуемая CSV-история — аналитический вывод, не источник истины для NPC.

## Совместимость

Снимки WORLD-0.4 не загружаются молча. Структура состояний, порядок некоторых эффектов, именование событий и поля JSON изменились. Для старых данных требуется явная миграция. Эта поставка включает готовые начальные сценарии нового формата, а не обещает автоматическую совместимость любых прежних файлов.

## E26. Метаданные не равны исполняемым коэффициентам

В исходном JSON некоторые поля выглядели как свободно изменяемые, хотя первая реализация фиксирует соответствующую политику в C++. Добавлен `PARAMETERS.md` с раздельным перечислением активных, фиксированных и зарезервированных полей. Нельзя считать JSON-каталог универсальным языком поведения или обещать, что любое поле управляет движком. Это исправление документации, не новый проходивший TDD функционал.

## E27. Одноэлементный вложенный JSON-массив в C++-фикстуре

Проверка Clang воспроизвела сбой C08: `Array{Array{60,120}}` в использованной связке давал `[60,120]`, тогда как GCC давал `[[60,120]]`. Изолированный пример подтвердил различие выбора конструкторов; это ошибка неоднозначно записанной тестовой фикстуры, не формулы расписания. Фикстура заменена на `encode(std::vector<std::vector<Minute>>{{60,120}})`. Реальный JSON сценария и его загрузка остаются прежними. Повторяются оба компилятора и sanitizers.


## E28. T0: ожидание обмена блокировало текущие потребности

Контроллер возвращал `await_response`/`await_handoff` с обязательной A01 раньше еды,
сна и остальной бытовой политики. При наличии готовой порции N01 падала ниже критического
порога. Чтение inbox также опережало доступную еду/сон.

Исправлено только принятие решения: после проверок недоступности/занятости и возобновления
маршрута доступная еда при `N01 <= activation` и сон при `N02 <= activation` проверяются
до inbox, proposals и задач acquire/repair. Ожидание обмена не завершает просмотр предложений
и не запрещает household выбрать работу, отдых или досуг. Когда других дел нет, остаётся
одноминутная A01 как обычный idle-fallback. Активные действия не прерываются автоматически.

Проверки: C10–C19, `T0_CLI_waiting_food`. Физические коэффициенты не менялись.

## E29. T0: прерванная A15 повторялась по устаревшему локальному соглашению

В локальной памяти соглашение могло оставаться accepted. Фильтр учитывал только completed
и сравнивал только proposal ID, поэтому interrupted вызывал повторные A15, а старый completed
мог блокировать другую версию. Для собственной A15 терминальность теперь означает совпадение
`(proposal, version)` и статус `completed` либо `interrupted`. Статус `rejected` не терминален:
после несовпавшей текущей готовности участники могут повторно подать собственные команды.

Legacy A13 не содержит version в request; её прежняя проверка completed по proposal сохранена.
Контроллер использует только собственные receipts, без чтения скрытого мирового состояния.
Проверки: C20–C25, CLI interrupted/completed/resume_interrupted/retry_readiness.
